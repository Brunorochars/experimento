# Revisão de código: `carrinho.py`

Encontrei **3 defeitos funcionais**. Ao final há uma observação de menor gravidade, que não classifico como defeito.

## Defeito 1: `adicionar` aceita quantidade zero

**(1) Localização:** `Carrinho.adicionar`, na linha `if quantidade < 0:`.

**(2) Descrição:** Uma chamada como `adicionar(codigo, 0)` não lança exceção. O produto entra no carrinho com quantidade 0, ou a quantidade existente fica inalterada.

**(3) Justificativa:** A RC03 exige que a quantidade seja "maior ou igual a 1 (`ValueError`)". A condição atual só rejeita valores negativos, então 0 passa. Isso também cria itens com quantidade 0 no carrinho. Esses itens:
- aparecem em `itens()`;
- fazem `total()` cobrar frete de R$ 25,00 sobre um subtotal 0, porque `self._itens` não fica vazio;
- impedem que `finalizar()` lance `CarrinhoVazioError`.

**(4) Correção:**
```python
if quantidade < 1:
    raise ValueError("quantidade inválida")
```

## Defeito 2: a verificação de estoque ignora a quantidade já presente no carrinho

**(1) Localização:** `Carrinho.adicionar`, na linha `if quantidade > produto.estoque:`.

**(2) Descrição:** Só a nova quantidade é comparada com o estoque. Exemplo com estoque 5: `adicionar(c, 3)` seguido de `adicionar(c, 3)` resulta em 6 unidades no carrinho, sem erro.

**(3) Justificativa:** A RC04 diz que "a quantidade total de um produto no carrinho (a que já estava mais a nova) não pode ser maior que o estoque". A variável `atual` é calculada, mas não entra na comparação. Uma consequência é que `finalizar()` pode deixar o estoque negativo, o que contraria a invariante da RC01.

**(4) Correção:**
```python
atual = self._itens.get(codigo, 0)
if atual + quantidade > produto.estoque:
    raise EstoqueInsuficienteError(f"estoque insuficiente para {codigo}")
self._itens[codigo] = atual + quantidade
```
Como a exceção é lançada antes da atribuição, o carrinho não é alterado, conforme pede a RC04.

## Defeito 3: os descontos são aplicados na ordem errada

**(1) Localização:** `Carrinho.total`, na linha `valor = (subtotal - desconto_cupom) * (1 - percentual / 100)`.

**(2) Descrição:** O código subtrai os R$ 20,00 do cupom antes de aplicar o percentual progressivo. Na prática, o percentual também incide sobre o valor do cupom, que deixa de valer R$ 20,00.

**(3) Justificativa:** A RC10 diz que o `DESC20` "abate R$ 20,00 do valor **depois** de aplicado o desconto progressivo". A RC12 define o total como subtotal − desconto progressivo − desconto do cupom + frete. Exemplo com subtotal de R$ 500,00 e cupom `DESC20`:
- **Esperado:** 500 − 50 − 20 = **430,00**, mais frete de 25 (pois 430 ≥ 300 dá frete 0). Total: **R$ 430,00**.
- **Obtido:** (500 − 20) × 0,9 = **432,00**.

A diferença também pode mudar o frete, já que a RC11 depende do valor após os descontos. Assim, o total pode ficar perto do limite de R$ 300,00 e cair do lado errado.

**(4) Correção:**
```python
valor = subtotal * (1 - percentual / 100) - desconto_cupom
valor = max(valor, 0.0)
return round(valor + self._frete(valor), 2)
```

## Observação (não classificada como defeito)

**`subtotal()` arredonda o resultado para 2 casas.** Os requisitos só mencionam arredondamento do total (cabeçalho e RC12). A RC07 define o subtotal como a soma simples. Com preços em centavos, o arredondamento só elimina ruído de ponto flutuante, o que é benéfico. Se houver preços com mais de 2 casas decimais, porém, ele pode mudar a faixa de desconto da RC08. Um subtotal de 499,996, por exemplo, viraria 500,00 e receberia 10%. Como os requisitos não dizem nada sobre preços com mais de 2 casas, registro isso apenas como ponto de atenção.

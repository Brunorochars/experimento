# Revisão de código: `reservas.py`

Encontrei **3 defeitos funcionais** e uma observação menor.

## Defeito 1: Capacidade máxima da sala não é validada (RR03)

**(1) Localização:** `SistemaReservas._validar`, na verificação de `participantes`.

**(2) Problema:** O código só verifica o limite inferior (`participantes < 1`). Não verifica se o número de participantes ultrapassa a capacidade da sala.

**(3) Justificativa:** A RR03 exige que "o número de participantes deve ser no mínimo 1 e **no máximo a capacidade da sala**". Por exemplo, numa sala com capacidade 10, `reservar(..., participantes=50, ...)` é aceito e cria a reserva, quando deveria lançar `ReservaInvalidaError`.

**(4) Correção:**
```python
if participantes < 1 or participantes > self._salas[sala]:
    raise ReservaInvalidaError("número de participantes inválido")
```

## Defeito 2: Reservas encostadas são tratadas como conflito (RR04)

**(1) Localização:** `SistemaReservas._conflita`, na condição `if inicio <= r.fim and fim >= r.inicio`.

**(2) Problema:** A comparação usa operadores inclusivos (`<=` e `>=`). Com isso, intervalos que apenas se tocam nas extremidades são considerados sobrepostos.

**(3) Justificativa:** Os intervalos são semiabertos `[inicio, fim)`. A RR04 diz: "Reservas encostadas não se sobrepõem: se uma termina às 10, outra pode começar às 10." Com o código atual, existindo uma reserva [8, 10), uma nova [10, 12) satisfaz `10 <= 10 and 12 >= 8` e lança `ConflitoDeHorarioError` indevidamente. O mesmo vale no sentido inverso: uma nova reserva [6..8) não é possível, mas [8, 10) contra uma existente [10, 12) também é rejeitada.

**(4) Correção:**
```python
if inicio < r.fim and fim > r.inicio:
    return True
```

## Defeito 3: Reservas canceladas continuam bloqueando o horário (RR04 e RR05)

**(1) Localização:** `SistemaReservas._conflita`, no laço sobre `self._reservas.values()`.

**(2) Problema:** O laço considera todas as reservas, inclusive as canceladas, porque não verifica `r.ativa`.

**(3) Justificativa:** A RR04 restringe o conflito a "duas reservas **ativas**". A RR05 determina que a reserva cancelada "libera o horário para novas reservas". Por exemplo: ao reservar [10, 12), cancelar essa reserva e tentar reservar [10, 12) de novo, o sistema lança `ConflitoDeHorarioError`. Note que `horarios_livres` e `ocupacao` mostram o horário como livre, pois usam `listar`, que filtra por `ativa`. Isso torna o comportamento do sistema inconsistente.

**(4) Correção:**
```python
def _conflita(self, sala, data, inicio, fim):
    for r in self._reservas.values():
        if r.ativa and r.sala == sala and r.data == data:
            if inicio < r.fim and fim > r.inicio:
                return True
    return False
```
Outra opção é reaproveitar `self.listar(sala, data)`, que já filtra as reservas ativas.

## Observação (risco menor, não é violação direta)

**Localização:** `_validar`, na verificação da data.

`datetime` é subclasse de `date`, então `isinstance(data, date)` aceita um objeto `datetime`. Em seguida, a comparação `data < self._hoje` entre `datetime` e `date` lança `TypeError` em vez de `ReservaInvalidaError`. A RR03 pede "um `date`". Se a intenção for rejeitar `datetime`, uma correção possível é:
```python
if not isinstance(data, date) or isinstance(data, datetime) or data < self._hoje:
```
Isso exige importar `datetime`. Como os requisitos não tratam explicitamente desse caso, considero apenas um ponto de atenção.

# Revisão de código: `notas.py`

Comparei cada requisito com o código. A lógica principal está correta: a ordem das regras em `situacao`, os pesos, o limite de 75%, a fórmula do exame e a ordenação do ranking batem com a especificação. Encontrei **dois defeitos**, ambos com a mesma causa: valores `NaN` passam pelas validações de intervalo.

---

### Defeito 1: nota `NaN` é aceita como válida (RN03 e RN07)

1. **Localização:** `Turma._validar_nota`, na linha `if nota < 0 or nota > 10:`.

2. **Descrição:** `float("nan")` é do tipo `float` e passa pela checagem de tipo. Como toda comparação com `NaN` retorna `False`, `nan < 0` e `nan > 10` são falsas e nenhuma exceção é lançada. A nota é então gravada em `aluno.notas` ou em `aluno.exame`.

3. **Justificativa:**
   - A RN03 exige nota "entre 0 e 10, inclusive", com `NotaInvalidaError` fora desse intervalo. `NaN` não pertence ao intervalo, mas é aceito.
   - O erro se propaga:
     - `media()` passa a retornar `nan`.
     - Em `situacao()`, `nan >= 7.0` e `nan < 5.0` são ambos falsos, então um aluno sem média válida cai em `"Exame"`.
     - Com exame `NaN`, `media_final()` retorna `nan` e o aluno fica `"Reprovado"`.
     - Em `ranking()`, a chave `-nan` torna a ordenação imprevisível, o que viola a RN09.
   - A RN07 usa a mesma validação, então `lancar_exame` herda o defeito.

4. **Correção:** escrever a condição de forma positiva, para que `NaN` falhe:
   ```python
   def _validar_nota(self, nota):
       if isinstance(nota, bool) or not isinstance(nota, (int, float)):
           raise TypeError("nota deve ser numérica")
       if not (0 <= nota <= 10):
           raise NotaInvalidaError("nota fora do intervalo")
   ```
   Outra opção é adicionar `math.isnan(nota)` à condição.

---

### Defeito 2: frequência `NaN` é aceita (RN04 e RN06)

1. **Localização:** `Turma.registrar_frequencia`, na linha `if not 0 <= percentual <= 100:`. O efeito aparece em `situacao`, na linha `if aluno.frequencia < FREQUENCIA_MINIMA:`.

2. **Descrição:** à primeira vista a expressão parece cobrir o caso, mas vale testar. Para `percentual = nan`, `0 <= nan` é `False`, então a cadeia `0 <= nan <= 100` é `False` e `not False` é `True`. Logo, **o `ValueError` é lançado**.

   Refazendo a análise: a forma `not (a <= x <= b)` já rejeita `NaN` corretamente. **Este ponto não é um defeito**, e o registro aqui serve para mostrar o contraste com o Defeito 1. Lá, a condição é escrita como `nota < 0 or nota > 10`, que deixa `NaN` passar. Aqui, a forma usada é justamente a correção sugerida acima.

### Pontos verificados sem defeito

- **RN01:** checa duplicidade, valida nome não vazio e aplica `strip()`. Correto.
- **RN02:** todas as operações públicas por matrícula passam por `_aluno()`. Correto.
- **RN03:** avaliações restritas a `P1`, `P2` e `T`; booleanos rejeitados com `TypeError`; relançar substitui a nota. Correto, exceto o caso `NaN`.
- **RN04:** limites 0 e 100 inclusivos. Correto.
- **RN05:** pesos 0,35, 0,35 e 0,30; avaliação ausente conta como 0; arredondamento para 2 casas. Correto.
- **RN06:** ordem das regras correta; 75% exatos não reprovam; faixa de exame [5,0; 7,0). Correto.
- **RN07:** exige situação `"Exame"`. Depois que o exame é lançado, a situação deixa de ser `"Exame"`, então um novo lançamento é bloqueado. Isso é coerente com o requisito.

**Resumo:** há **um defeito funcional confirmado**: `_validar_nota` aceita `NaN`, o que afeta RN03, RN07 e, por consequência, RN06, RN08 e RN09. O restante do código está conforme os requisitos declarados.

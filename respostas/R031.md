# Revisão de código: `carrinho.py`

Encontrei **3 defeitos funcionais**. O restante do código está de acordo com os requisitos.

## Defeito 1: `adicionar` aceita quantidade zero (RC03)

**(1) Localização:** `Carrinho.adicionar`, linha `if quantidade < 0:`.

**(2) Problema:** a condição rejeita apenas valores negativos. Por isso, `quantidade = 0` é aceita.

**(3) Justificativa:** a RC03 exige quantidade "maior ou igual a 1", com `ValueError` nos demais casos. Com o código atual, `adicionar("P1", 0)` não lança exceção. Se o produto ainda não estava no carrinho, ele passa a constar em `_itens` com quantidade 0. Isso aparece em `itens()` como `{"P1": 0}` e faz o carrinho deixar de ser considerado vazio em `total()` e `finalizar()`. Por exemplo, `finalizar()` retornaria 25.0 (só o frete) em vez de lançar `CarrinhoVazioError`.

**(4) Correção:**
```python
if quantidade < 1:
    raise ValueError("quantidade inválida")
```

## Defeito 2: a verificação de estoque ignora a quantidade já no carrinho (RC04)

**(1) Localização:** `Carrinho.adicionar`, linha `if quantidade > produto.estoque:`.

**(2) Problema:** só a nova quantidade é comparada com o estoque. A variável `atual` é calculada, mas não entra na verificação.

**(3) Justificativa:** a RC04 determina que "a quantidade total de um produto no carrinho (a que já estava mais a nova)" não pode exceder o estoque. Exemplo com estoque 5:
- `adicionar("P1", 3)` funciona.
- `adicionar("P1", 3)` deveria lançar `EstoqueInsuficienteError`, mas o código aceita e deixa 6 unidades no carrinho.

Como consequência, `finalizar()` pode deixar o estoque negativo, o que contraria a invariante da RC01.

**(4) Correção:**
```python
atual = self._itens.get(codigo, 0)
if atual + quantidade > produto.estoque:
    raise EstoqueInsuficienteError(f"estoque insuficiente para {codigo}")
self._itens[codigo] = atual + quantidade
```

## Defeito 3: o cupom DESC20 é aplicado antes do desconto progressivo (RC10/RC12)

**(1) Localização:** `Carrinho.total`, linha `valor = (subtotal - desconto_cupom) * (1 - percentual / 100)`.

**(2) Problema:** os R$ 20,00 são subtraídos do subtotal e só depois o percentual é aplicado. Assim, o próprio cupom sofre o desconto progressivo e vale menos de R$ 20,00 sempre que o percentual for maior que zero.

**(3) Justificativa:** a RC10 diz que o DESC20 "abate R$ 20,00 do valor **depois** de aplicado o desconto progressivo". A RC12 define total = subtotal − desconto progressivo − desconto do cupom + frete, e o desconto progressivo incide "sobre o subtotal" (RC08). Exemplos:
- **Subtotal 500,00 com DESC20:** o esperado é 500 × 0,90 − 20 = **450 − 20 = 430,00**, com frete 0. O código calcula (500 − 20) × 0,90 = **432,00**.
- **Subtotal 200,00 com DESC20:** o esperado é 200 × 0,95 − 20 = 170,00, mais 25 de frete, totalizando **195,00**. O código calcula 180 × 0,95 + 25 = **196,00**.

O erro também pode alterar a decisão do frete (RC11), porque o valor comparado com R$ 300,00 sai diferente.

**(4) Correção:**
```python
valor = subtotal * (1 - percentual / 100) - desconto_cupom
valor = max(valor, 0.0)
return round(valor + self._frete(valor), 2)
```

## Itens verificados sem defeito

- **RC01:** a validação de preço e estoque está correta.
- **RC02:** o carrinho começa vazio e sem cupom.
- **RC05:** `remover` está correto. Sem quantidade, o item inteiro sai do carrinho. A faixa de 1 até a quantidade no carrinho é respeitada, e o item é removido quando o restante chega a zero.
- **RC06:** `itens()` retorna uma cópia.
- **RC07:** `subtotal()` soma preço × quantidade.
- **RC08:** as faixas de 10%, 5% e 0% estão corretas.
- **RC09:** o cupom é normalizado com `strip().upper()`, códigos inválidos são rejeitados e um novo cupom substitui o anterior.
- **RC10:** o mínimo de R$ 100,00 é verificado sobre o subtotal.
- **RC11:** o frete usa o valor após os descontos e trata o FRETEGRATIS. O resultado só fica incorreto por causa do Defeito 3.
- **RC12:** o valor antes do frete nunca fica negativo, e o carrinho vazio retorna 0.
- **RC13:** `finalizar` lança erro com carrinho vazio, calcula o total antes de alterar o estado, baixa o estoque, limpa os itens e o cupom e retorna o total.

**Observação (não é defeito):** `subtotal()` arredonda o resultado para 2 casas. Os requisitos só exigem arredondamento do total e não proíbem isso, então não classifico como defeito. Com preços de mais de 2 casas decimais, esse arredondamento poderia afetar marginalmente as faixas de desconto.

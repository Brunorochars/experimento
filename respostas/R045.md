# Revisão de código: `reservas.py`

## Conclusão

**Não encontrei defeitos funcionais.** O código atende aos requisitos RR01 a RR09 como estão escritos.

## Verificação por requisito

| Req. | Trecho | Resultado |
|---|---|---|
| RR01 | `__init__`: `if capacidade < 1: raise ValueError` | Correto. Capacidade 0 ou negativa lança `ValueError`. |
| RR02 | `reservar` / `_proximo_id` | Correto. Os ids começam em 1. O contador só avança depois que a validação e o teste de conflito passam, então reservas rejeitadas não consomem id. |
| RR03 | `_validar` | Correto. Todas as regras lançam `ReservaInvalidaError`: sala inexistente, data não-`date` ou anterior a hoje, horários não inteiros (`bool` também é rejeitado), `inicio < 8` ou `fim > 22`, `inicio >= fim`, duração acima de 4, participantes fora de [1, capacidade] e responsável vazio ou só com espaços. O `strip()` é aplicado ao salvar. |
| RR04 | `_conflita`: `inicio < r.fim and fim > r.inicio` | Correto. É o teste de sobreposição de intervalos semiabertos. Reservas encostadas (10–12 e 12–14) não conflitam. Só considera reservas ativas, da mesma sala e da mesma data. |
| RR05 | `cancelar` | Correto. Id inexistente lança `ReservaInexistenteError` e reserva já cancelada lança `ReservaInvalidaError`. Como `_conflita` filtra por `r.ativa`, o horário cancelado fica livre. |
| RR06 | `buscar` | Correto. Retorna a reserva ativa ou cancelada; id inexistente lança `ReservaInexistenteError`. |
| RR07 | `listar` | Correto. Filtra as ativas por sala e data e ordena por `inicio`. |
| RR08 | `horarios_livres` | Correto. `range(8, 22)` gera as horas 8 a 21, e `range(r.inicio, r.fim)` marca as horas ocupadas no intervalo [início, fim). Sala inexistente lança `ReservaInvalidaError`. |
| RR09 | `ocupacao` | Correto. Calcula `(14 − livres) / 14 × 100` com `round(..., 1)`. Os valores possíveis são k × 100/14, e nenhum cai exatamente em um empate de arredondamento. Por isso o arredondamento bancário do Python não altera o resultado. |

## Observações (não são defeitos, pois os requisitos não definem esses casos)

1. **`_validar`, checagem da data:** um `datetime` passa em `isinstance(data, date)`, porque é subclasse de `date`. Mas a comparação `data < self._hoje` com um `date` lança `TypeError`, e não `ReservaInvalidaError`. Os requisitos não dizem se `datetime` é aceito. Se a intenção for rejeitá-lo, uma correção possível é usar `type(data) is date` ou `isinstance(data, datetime)` → erro.
2. **`_validar`, participantes:** o tipo não é validado. Uma string gera `TypeError`, e `True` é aceito como 1. Os requisitos não especificam o tipo.
3. **`listar` e `ocupacao` sem validar a data:** os requisitos não exigem essa validação, então não é defeito.
